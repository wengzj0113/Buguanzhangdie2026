# 篮子数量模式 3：技术方案

日期：2026-10-20。状态：需求已确认，编码与验证进行中；完成状态以验证目录的实际证据为准。

## 1. 行为约定

`篮子数量=3` 是新的运行模式。初次入场仍建立两个篮子，方向相反、首单手数相同；它不表示初次开三个篮子。

设首次建立 A、B 两个篮子。A 结束，B 仍在运行；B 随后发生现有策略允许的止损换单，换单首单确认成交后，新增 C 篮子。C 的首单方向与 B 本次换单首单相反，首单手数与 B 本次换单首单的实际成交总手数相同。B、C 成为新的一对；以后满足同样条件时可以再次补开。

续配不限制代数：B 结束后，C 再有效止损换单可以补出 D。初始这一批篮子的延续链可能长期持续；单个篮子结束不等于整条链结束。没有新增整条链止盈、最大代数或统一重置规则。

示例：A 买 0.01，B 卖 0.01；A 止盈结束，B 后续按原规则换成买 0.03，则 C 同时启动卖 0.03。B 保留自己的循环阶段、反手次数、亏损累计；C 从独立首单阶段开始，循环索引及反手次数为 0，亏损累计为 0。

| 当前事实 | 模式 3 的动作 |
| --- | --- |
| 新信号满足原首单条件 | 按现有双篮子入口建立 A、B |
| A、B 都还在运行，B 止损换单 | 只执行 B 的原换单，不新增第三个篮子 |
| A 结束，B 继续持有，尚未止损换单 | 继续管理 B，不立即补开 |
| A 结束，B 的止损换单首单成交且保护确认 | 为该次换单建立一个反向等手数的新篮子 C |
| A 结束，但 B 的换单请求失败或结果未明 | 不提前开 C；按原恢复流程核对 B |
| B 触及反手上限、超量终止或触发全局重置，未形成有效换单首单 | 不为该终止事件开 C |
| A、B 都结束 | 结束这一对；后续首次入场仍按原信号规则执行 |
| 只是网格成交、移动保护、人工处理或参数重载 | 不单独产生补开事件 |

“反手”的方向仍由现有循环序列决定。有些循环阶段可能连续同方向开单，新模式不强制改写循环；C 始终反向于本次实际换单首单。

“同时”按交易执行解释为同一次止损换单事件内的两个交易请求：先确认换单首单，再尽快提交 C。经纪商不能保证两个请求在同一时刻、同一价格成交；各篮子按自己的实际成交价建立保护。

## 2. 范围与现有源码事实

本方案覆盖两个兼容主入口及十种固定距离模式共用的双平台核心：

- `NoMatterRiseFall_MT4.mq4`、`NoMatterRiseFall_MT5.mq5`。
- `NoMatterRiseFall_MT4_Core.mqh`、`NoMatterRiseFall_MT5_Core.mqh`。
- 现有 20 个固定模式 `.mq4/.mq5` 薄入口通过核心获得功能，通常无需改入口文件。
- 新增有针对性的测试与回放脚本，更新 `README.md` 和 `EA软件使用手册.html`。

独立的 `NoMatterRiseFall_*_XAU_NetRR_v2_10` 含自己的成本预算和策略扩展，本轮不扩展该产品；已有 XAU 测试仍需通过。修改测试时必须区分本轮四个目标和旧 XAU 参数契约。

2026-10-20 工作树已有大量未提交源码、测试、字节码及文档变化，实施基线必须来自当前文件，不能只检出 HEAD。不要覆盖、清理或把这些既有变化混入本功能提交。

已核对的入口和风险：

| 位置 | 已有实现 | 本功能接入 |
| --- | --- | --- |
| MT4 `StartResolvedMultiPair`、MT5 `MultiStartResolvedPair` | 接收已计算的首单方向、手数和锁定距离 | 模式 3 首次入场复用，额外登记持久配对关系 |
| MT4 `StartInitialMultiOco`、MT5 `MultiStartCandleOcoPair` | K 线每根一次的高低点 OCO；一侧成交后建立反向篮子 | 完整保留 OCO 语义，首次配对完成后登记模式 3 |
| `MultiHandleReverseFill` | 已有反手挂单成交后提升到下一循环阶段 | 记录一次止损换单事件及其成交结果 |
| `MultiRecoverFlatGroupAfterBrokerStop` | 券商先平仓，EA 再补下一阶段市价单 | 同一事件记录与确认入口 |
| `MultiManageGroup` | 主动检测止损、市价换单、`transition_target_lots` 恢复补单 | 同一事件记录与确认入口；恢复不再计数 |
| `MultiSaveGroup/LoadGroups/ResetState/StateChanged/DeleteState` | 现有独立组持久化 | 增补归属和止损事件序号 |
| `ManageAllMultiGroups`、`ManageMultipleCandleGroups` | 遍历管理中会删除、移动数组项 | 完成遍历后才处理模式 3 新建篮子 |

MT5 的 `pair_role/pair_peer_id` 在首单完成后会清零，不能承担长期配对关系。MT4 的 `pair_parent_id/pair_peer_id` 也参与启动及 OCO；部分逻辑还复用 `initial_low_direction` 恢复启动关联。本轮新增独立字段，不扩展这些临时字段的含义。

核心文件比兼容入口多了请求未决隔离和重试退避。仅移植本功能增量，不用兼容入口整段替换核心，也不顺带统一整套交易管理器。

当前 `MultiTryOpenCandleGroup` 在模式 2 且存在活动组时直接阻止新一对入场。模式 3 延续这一现行限制；不借本功能修改 K 线多组的并发策略。无论将来允许多少独立入场事件，补开资格都只能在同一配对内判定。

MT4 现有达到最大反手次数的分组路径调用全局重置；MT5 对双篮子已有组内结束路径。保留各自当前行为，模式 3 在任何终止/重置路径都不得发起补开。本功能不包含反手上限行为的双平台重构。

## 3. 方案选择

1. **采用：独立配对记录 + 原换单路径挂钩 + 遍历后补开。** 复用现有方向、距离、手数、保护、拆单和恢复代码，新增逻辑只决定是否、何时为一次已确认换单建立 C。
2. 直接查看全局活动组数量，少于 2 就补开。实现较短，但会把旧单、其他入场事件、失败待查请求混在一起，无法满足条件和恢复要求，不采用。
3. 重写整个单/双篮子管理器为统一引擎。涉及既有循环、网格和平台差异，修改面明显超过本需求，不采用。

新增代码在四个现有目标文件内形成同名、小范围的模式 3 模块，不拆分现有大文件，不改变旧管理器的接口。两平台使用同一状态约定、事件规则和测试矩阵。

## 4. 身份、状态与持久化

### 4.1 组归属

`MultiGroupState` 新增三个归属字段：

```cpp
int basket_mode_at_start;  // 0=旧记录，无补开；新记录为 1/2/3
int basket_family_id;      // 初次配对分配的永久 family ID
int stop_event_sequence;   // 本篮子止损换单事件的递增序号
```

执行层另保存当前分笔请求的 `renewal_request_state`、`renewal_deal_cursor`、`renewal_request_direction`、`renewal_request_volume_before`，并用 `.rrcommit` 标记元数据是否越过发送边界。成交游标拆成两个32位部分持久化。下一分笔的 family 待发送记录提交前，先提交“上一笔已结束、本笔尚未发送”的状态，防止把上一笔票据当成本笔已发送证据。成交核对按当前方向与游标，不能以净持仓必须增加作为唯一依据：早先分笔可能已经平仓。

与既有字段一同覆盖初始化、保存、读取、脏状态比较和删除。缺失字段的旧记录按 0 处理，不猜测旧订单属于模式 3。模式 3 只从本版本完整登记的新入场事件开始；修改输入值不把旧篮子转成模式 3。已经登记的模式 3 配对按其出生模式恢复和管理，不因输入改为 1/2 遗失未完成事件。

### 4.2 配对记录

新增独立的 `BasketFamilyState` 数组和终端全局变量记录，生命周期长于单个已结束组。`family_id` 使用本对原始首个组 ID，后续不变；`pair_generation` 每补开完成递增一次。

记录包含：版本、保存序号、family ID、出生模式、配对代次、两个当前成员 ID、双方状态（未知/运行/已确认结束）、双方结束所在管理批次，以及一个未完成的补开事件。事件字段包括来源组 ID、来源止损序号、发生批次、旧配对代次、旧对端 ID、对端在发生批次是否结束、原/目标循环索引和反手次数、目标方向、目标手数、锁定 SL/TP、循环模式、已确认首单手数、预分配新组 ID、执行阶段及失败原因。

事件唯一键为 `(family_id, pair_generation, source_group_id, stop_event_sequence)`。不要只用 K 线时间：同一根 K 线可能发生多次止损。不要只用循环索引：循环会回到 0。组 ID、代次、序号按 int 正数分配，溢出前拒绝新事件并保留现有管理。

`BasketFamilyState` 的两成员归属由配对记录维护；新 C 成交后以 B/C 替换 A/B，A 的结束事实可归档。B 的循环不重置；B 的 `stop_event_sequence` 不归零。

### 4.3 持久提交

模式1/2原组保存方式保持原样。四个宿主共用 `NoMatterRiseFall_BasketRenewal.mqh` 的模式3实现，避免四份状态机分叉。模式3配对记录单独使用两个槽位及最后写入的提交序号，避免多次 `GlobalVariableSet` 只写一半就被当作有效事件：

1. 新槽位的 valid 清零并 flush；逐项写入并检查写入结果。
2. 所有字段写入后 flush，最后写 valid=本次序号并 flush。
3. valid 自身即提交序号；旧的有效槽位保留到下一次轮换。恢复时读取最高的完整有效版本，字段不完整或版本不匹配不允许补开。
4. 分配并保存 child ID、事件键及未决请求意图后才能发送新 C 的交易请求。写入失败时不发 C，继续保护已存在持仓，记录失败。

模式3键使用独立紧凑前缀：原始服务器名、原始品种名及既有 StatePrefix（账户/Magic/profile）一起计算两个32位哈希，并逐字符保存完整作用域作碰撞核对。组状态与 MT5 所有权/配置指纹也使用该紧凑空间，避免原前缀附加字段后超过终端63字符上限。旧模式前缀不改；完成重置后删除模式3配置锁，避免影响后续模式1/2。全局变量中的事件 ID 使用安全整数，不把任意64位MT5成交票据直接转换double作为去重键。

已结束组在删除前，要先把结束事实提交到 family 记录。`MultiClearAll`、无资金清理及全局重置要取消并持久化补开意图；family 只有在无持仓、无挂单、无未决请求、无未完成事件时才可清除。重启必须先恢复、对账 family，再允许新信号入场。

## 5. 触发与执行顺序

模块的对外入口如下；实现可有私有辅助函数，但交易调用者只使用这些入口：

```cpp
bool BasketRenewalRegisterPair(const int mode, const int family_id,
                              const int first_id, const int second_id);
bool BasketRenewalPrepareStop(const int source_id, const int next_index,
                             const int next_direction, const double target_lots);
bool BasketRenewalConfirmFirstOrder(const int source_id,
                                   const int stop_sequence,
                                   const int actual_direction,
                                   const double actual_first_lots);
bool BasketRenewalRecordFinished(const int group_id);
void BasketRenewalProcess();
void BasketRenewalLoad();
void BasketRenewalCancelAll();
```

`PrepareStop` 对非模式 3 返回 true、无副作用。模式 3 在止损已确认、原有上限/超量/全局风控允许继续换单后调用；生成或恢复同一事件，在修改循环状态及发市价单前持久化。对反手挂单已经成交的路径，先核对该票据，再登记事件；不能因为登记失败去重复发送已经成交的换单。记录失败表示本次补开未获授权，不能仅因返回 false 就跳过必需的原换单或已有仓位保护；来源请求本身未决时则沿原隔离流程处理，禁止重发试探。

模式 3 的原换单进度也必须先保存再请求，事件记录的原/目标索引、反手次数和亏损累计用于恢复已推进的阶段，防止重启把同次亏损累加两遍。事件恢复按阶段核对，不能把 `transition_target_lots>0` 当成新止损事件。

`ConfirmFirstOrder` 在换单目标总量已成交、方向核对完成、旧阶段持仓/挂单清理完成、SL/TP 验证通过后调用；立即冻结该次首单的实际总量，再允许新阶段网格继续。多张拆单合计为一笔策略首单，未决和部分成交继续等待；不能从后来已经包含新网格的 `total_lots` 重新计算 C 手数。

管理循环每轮按以下顺序运行：

1. 对账本轮已知持仓、挂单、未决请求及结束事实，开启一个管理批次。
2. 按原流程逐个管理组。止损挂钩只登记/确认事件，结束挂钩只记录事实；不在持有数组元素引用时扩容。
3. 结束事实先持久化，再移除已结束组。结束须以该组无持仓、无挂单、无未决交易或换单目标为准；单纯查不到持仓、`active=false` 或临时断连都不够。
4. 完成所有旧组管理后执行 `BasketRenewalProcess`，处理事件、分配/恢复 child、创建 C，并用 ID 重新查询索引。
5. 再决定是否允许下一次原首单信号。未完成模式 3 事件也视为占用现有入场流程，不能因为暂时没有持仓而新开一对。

同一管理批次内出现“一篮子确认结束、另一个止损换单”的交叉情形，统一在本轮结束后判定；只要换单来源仍有效、对端已确认结束，允许补开一次，结果不依赖数组正向或反向遍历。若同批双方都终止、没有有效来源首单，则不补开。对端在更晚的管理批次才结束，不追溯触发此前发生且当时双方都运行的止损事件。历史或请求仍未知时保留待对账状态，不把未知当结束。

模式 3 不是“每次止损都复制一对”。同一 family 同时最多占用两个篮子位置，待补的 child、部分成交 child 和结果未明 child 均占用一个位置。一次事件只分配一个 child ID，重试复用该 ID。

若上一 child 尚未对账完毕，来源已发生下一次止损，保留旧事件及 child 身份并把它标为取消待对账；新止损的原交易照常管理，但不能覆盖旧记录或再预留第二个 child。旧事件确认无暴露且结束后，后续新的合格止损事件仍可补开；不追补已跳过的历史事件。

## 6. 补开状态机

| 阶段 | 含义与下一步 |
| --- | --- |
| `STOP_RECORDED` | 已持久记录止损事件；等待原换单和同批对端结束状态对账 |
| `PRIMARY_CONFIRMED` | 换单首单方向、首单总量和保护已确认；核定本事件资格 |
| `NO_RENEWAL` | 对端当时仍运行，或来源终止；本事件永久消费，不因以后少篮子而重放 |
| `CHILD_RESERVED` | 唯一 child ID 和冻结参数已保存，尚未发请求 |
| `CHILD_IN_FLIGHT` | 请求已发送/结果未明；只核对持仓、订单和历史，不盲目重发 |
| `CHILD_PARTIAL` | 已有部分成交；按冻结目标补剩余量，不能重发全额 |
| `PAIRED` | C 的方向、总量、保护均验证；当前成员更新为 B/C、代次加一；事件已消费 |
| `FAILED` | 永久拒绝或身份冲突；记录原因，管理已有风险，不自动分配另一个 child |
| `CANCELED` | 来源对应首单已终止/进入下一止损事件，或用户重置/全局清理；撤销未发送部分 |

`CHILD_RESERVED` 到发送前必须再次确认：来源组仍属于记录中的同一止损阶段，首单存在且保护完成；另一位置确实没有可归属持仓；事件没有被消费；没有 reset。补开方向取冻结的实际方向的反向，SL/TP 点数取来源篮子锁定值，循环模式取来源快照。

模式 3 未完成 child 的缺口发单只有续配模块负责。`MultiManageGroup` 原有 `transition_target_lots` 自动发送/补量入口必须先识别该 child，在完成未决请求核对与现有仓位保护后返回，交由遍历后的续配模块决定是否发送；否则通用恢复入口会绕过来源阶段检查。child 完成后清除该代管状态，恢复原组管理。取消后仍有部分或晚到成交时，先按实际量完成独立首单收养与保护、取消剩余目标，再交回原组管理；记录为取消后收养而非等量配对成功，并在 family 当前成员/占用状态中登记它。

新 C 使用独立组 ID、现有组注释和 Magic 作用域；首单手数/网格基准按它自己的实际成交量初始化，循环索引 0、反手次数 0、累计亏损 0、两个方向网格掩码和票据缓存清零。不得把 B 的 `cumulative_loss_lots`、`previous_grid_lots` 或网格层级复制给 C。MT5 将 C 继续标为已有双篮子成员，使现有组内反手上限清理路径生效。

## 7. 失败、重启与门控

- 原换单失败或结果未明：原路径恢复，C 等待；禁止为了补 C 重开一次来源首单。
- C 临时失败：保留唯一事件和 child ID，沿用当前平台/文件已有的请求核对、重试分类和退避；兼容入口缺少的模式 3 请求未决保护只补在新分支，不整体移植核心。每轮最多提交一次允许的缺口请求。
- C 永久失败：记录可诊断失败，继续管理 B；不能无期限每 tick 重发，不能为了补齐而关闭 B。
- 超时、断线、请求状态未知：先查现有持仓、订单和历史；确认没有接受且属于可重试失败后才重发。历史不可用时保持未知。
- C 部分成交/拆单：冻结目标是 B 的本次首单总手数，按现有 `BuildReversalLotPlan/MultiOpenMarket` 处理单笔上限及剩余量；在等量和保护核对完成前不得标为配对成功，也不放行 child 网格来污染首单量。若新 C 的完整总量因限制无法合法实现，显示失败，不静默缩手数冒充等量。
- 部分成交后若原开仓订单仍有有效余量，保留其占位，不发送第二份余量；原单明确结束/撤销后才允许补差额。取消或重置必须核对并撤销这类订单，包括 MT5 RETURN 市价单的在途余量。已成交的部分首单若在补齐前结束，取消继续补齐；后续晚到成交按实际量收养与保护，不重补已平仓的早先分笔。
- 来源首单在 C 补齐前终止或再次止损：未成交 child 不再迟到补开；取消缺口意图，核对并撤销尚可撤销的请求/挂单。已成交的 child 必须继续独立保护管理；若请求随后晚到成交，收养同一 child ID 的持仓，不分配第二个 child。已有部分成交计为占用位置，本轮不额外产生新补开链。
- 任何全局资金不足清理、显式重置均优先：先封存/取消意图，再执行现有清理，事件不得在下一 tick 或重启后复活。
- 原始新信号继续执行现有交易时段、点差、GUI、信号去重等检查。C 是已接受止损事件的续办，不重新等待新指标/K 线信号，也不重置初始信号消费锁；沿用该文件现有续办开单门控，不临时新增时间或点差规则。新 C 仍必须通过有效报价、交易权限、合法手数、保证金和止损距离等现有执行检查。GUI 的仅首单开关与显式停止/重置沿用各自现有语义。
- 模式 2/3 均要求 MT5 对冲账户；参数校验接受 1/2/3，其他值拒绝。恢复出模式 3 状态时也检查对冲条件，不因当前输入为 1 绕过。

不能从“没有查到”推导出“没有成交”。仅持有两方向仓位也不能推导出两者是本功能的一对。
